# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

FlickOS 2.0: a Debian 13 (trixie, amd64-only) live ISO with a labwc Wayland desktop and the Calamares installer. Almost nothing is compiled (only the `sfwbar` package). The repo holds the live-build config, a few native Debian packages, apt-repo tooling and CI. The detailed docs are in `docs/01`–`09` (numbered, read in order). `docs/01-overview.md` has a "Where to change what" table, and `docs/07-troubleshooting.md` covers known failures.

**Design guidelines:** `docs/hig/` (FlickOS's HIG) says how every package must look, behave, read and be built. New work follows it, and a change is reviewed against `docs/hig/checklist.md` (its Must rules). `docs/hig/audit.md` lists where existing packages fall short: delete a row when you fix it, and update the HIG, checklist and audit together when a rule changes.

## Commands

Build host must be Debian 13: `sudo apt install live-build build-essential debhelper dpkg-dev devscripts reprepro rsync wget qemu-system-x86 qemu-utils ovmf xorriso meson pkgconf gettext libgtk-3-dev libgtk-layer-shell-dev libjson-c-dev libwayland-dev wayland-protocols` (the last group is sfwbar's Build-Depends)

```sh
tools/build-iso.sh [--purge]   # clean + packages/build.sh + lb config + sudo lb build → FlickOS-64bit-vX.Y.iso, SHA256SUMS, build.log (30–50 min). --purge for releases
tools/release.sh [--no-publish] X.Y   # release prep: bump version in flickos-release + branding.desc, dch both packages, repo/publish.sh + repo/upload.sh, wait for InRelease. Commits nothing
tools/boot-test.py [-v] [--iso FILE]   # headless QEMU boot test on serial console (runs in CI); results in boot-test/
tools/test-iso.sh [--live|--install|--disk] [--uefi|--bios] [--reset]   # QEMU window; test disk in .test-vm/
sh packages/build.sh           # build all packages/* into config/packages.chroot/ (needs repo public key)
repo/community/publish.sh   # community apps CI built on main → trixie-community (gh; --from DIR for a trial), then repo/upload.sh
repo/community/build.py [--allow-local] [--base REF] NAME   # what community CI does: clone the pinned commit, build, check.py, diff
python3 -m unittest discover -s repo/community/tests   # the community checks' tests
repo/publish.sh && repo/upload.sh   # add built .debs to the signed reprepro repo, plus EXTRAS (proprietary apps from ../flickos-notes etc., free of charge until the store opens: store ADR-008; never in the ISO), push to dvbondoy.github.io/flickos-apt (GitHub Pages)
lintian config/packages.chroot/flickos-settings_*.deb
tools/package-cost.py PKG|FILE.deb   # HIG PERF-7 disk cost: packages + KB it adds to the image (vs the last build's flickos-amd64.packages; --host: vs this computer)
tools/measure.py [--tree] PID | -- COMMAND   # HIG PERF-7: CPU, PSS/Private, wakeups/min from /proc until it exits
```

Single package by hand: `cd packages/NAME && dpkg-buildpackage -us -uc -b`. This leaves build output in the source tree (`debian/.debhelper/`, `debian/NAME/`, `../*.deb` and so on), so clean it up afterwards. `build.sh` avoids that by building in a copy under `packages/.build/`.

Fast iteration without a full rebuild: `sudo lb clean --binary && sudo lb build 2>&1 | tee -a build.log` keeps the populated `chroot/` and re-runs hooks and image creation. After an interrupted build, plain `sudo lb build` resumes. See `SESSION_COMMANDS.md` for the rename/checksum steps and chroot patching.

Boot-test exit codes: 0 pass, 1 check failed, 2 setup error, 3 no login. Checks are the `CHECKS` list at the top of `tools/boot-test.py`. Add one when you add a user-visible feature.

## Architecture

There are two delivery paths, and changes must work for both:
1. **ISO** (`lb build`): a snapshot for new installs.
2. **Apt repo** (`repo/`): the only way installed systems get FlickOS changes.

So customizations go into `.deb` packages under `packages/`, not into files dropped straight into the image (`config/includes.*`), because those never update after install. Use live-build config only for things that apply only to the live image or to the build itself.

- `auto/config` is the **single source** of all `lb config` options. `auto/clean` deletes the generated `config/{binary,bootstrap,chroot,common,source}` so removed options don't persist. Never edit generated/git-ignored live-build output (`chroot/`, `binary/`, `cache/`, `.build/`, `config/binary` and the like, `config/packages.chroot/`, hook symlinks numbered 1000+).
- `packages/build.sh` stages .debs into `config/packages.chroot/`. live-build turns that folder into a local apt repo, so the ISO always contains the packages as they are in the working tree.

## Invariants to preserve

- **Version:** `FLICKOS_VERSION` in `packages/flickos-branding/usr/lib/flickos-release` is the single source. It drives the ISO name, volume label, os-release, SourceForge folder and boot test. The only other copy is `packages/flickos-installer/etc/calamares/branding/flickos/branding.desc` (`version`, `shortVersion`, `versionedName`, `shortVersionedName`). `build-iso.sh` aborts if they differ. CI rejects a tag other than `v$FLICKOS_VERSION`.
- **Package versions:** any content change to a package needs a changelog bump: `dch -i -D trixie "Message."` (never edit `debian/changelog` by hand, never leave `UNRELEASED`, no `-1` suffix). apt only upgrades to higher versions, and reprepro rejects a changed file at an existing version. When the change adds a dependency, bump the depending package too.
- **Palette:** every FlickOS component (waybar, foot, fuzzel, mako, labwc theme, swaybg/swaylock, boot menus, Plymouth, Calamares, login screen, `tools/make-placeholder-art.sh`, `tools/make-layout-previews.sh`) uses arc-theme's Arc-Dark colors; only the Light style's files (`styles/light/*`, `FlickOS-Arc` themerc) use Arc's light colors, flickos-style-seven's Seven its own (`ALLOWED_SEVEN`, ADR-013) and flickos-style-aye3's Aye3 its own (`ALLOWED_AYE3`, ADR-014), flickos-style-footprint's Footprint its own (`ALLOWED_FOOTPRINT`, ADR-016) and flickos-style-elemental's Elemental its own (`ALLOWED_ELEMENTAL`, ADR-017), and boot menus, splash and installer stay Arc-Dark. Users' own styles may use any colors; the palette's key names are frozen (HIG VIS-10). FlickOS's brand amber `#ffb13d` (text on it `#2f343f`) is only on the brand surfaces: logo, boot menus, Plymouth, installer, artwork, and on the desktop only the start button's logo (ring and dot of `flickos-symbolic.svg`, class `warning`, recolored by `-gtk-icon-palette: warning @brand_color` in base.css; `brand_color` in each style's `waybar-colors.css`, `#c98000` on Light); the desktop stays Arc's blue (`docs/design/flickos-accent.md`; the Light wallpaper's deeper `#c98000`). `tools/check-palette.py` holds both allowed lists, `BRAND` (only in `BRAND_FILES`) and valid labwc theme keys, and checks that every style's foot/fuzzel/mako palette sets exactly the base configs' color keys; `build-iso.sh` aborts on a stray color. Add new colors there deliberately.
- **Menus:** the live menu (`flickos-installer`) is the installed menu (`flickos-settings`) plus *Install FlickOS* and a separator. Change both; `tools/check-menus.py` (run by `build-iso.sh`) fails otherwise.
- **Layout overlay:** the chosen desktop layout is applied only through generated files in `$XDG_RUNTIME_DIR/flickos/` (regenerated at every login, written atomically, deleted when not needed). Never copy FlickOS config into `$HOME`, and never modify user files (`~/.config/waybar`, `~/.config/labwc/rc.xml`). Warn about them (`flickos-layout doctor`) instead. `set` restarts only waybar processes whose `-c` is under `/usr/share/flickos/` or the overlay.
- **License:** FlickOS is GPL-3.0-or-later (`LICENSE`). Every package has a DEP-5 `debian/copyright`: `Files: *` is FlickOS's own work (GPL-3+), and every file from elsewhere has its own stanza (Unsplash wallpapers in flickos-layouts and flickos-settings' `default.jpg`, the Calamares settings from calamares-settings-debian ISC). Adding such a file means adding its stanza; a new package needs a `copyright`. The name and the halo logo are trademarks (`TRADEMARKS.md`: a changed system needs its own name and logo; package, command and ID names are not covered); `flickos-branding`'s `copyright` has a `Files:` stanza for the logo files with the GPL-3 7(e) note, and flickos-installer (`logo.png`, `flickos-install.png`) and flickos-layouts (the Dark/Light wallpapers) get the same stanza at their next version. A new file that shows the logo goes in its package's stanza and in TRADEMARKS.md's list if it's a new place.
- `Enabled: no` in `flickos.sources` is an offline-testing hack only. It must not be committed for a release (build-iso warns, boot-test fails).
- The ISO build's final `apt update` needs the published apt repo to be online. `packages/build.sh` needs `keyrings/flickos-archive-keyring.asc`, and `repo/publish.sh` needs a real `SignWith` in `repo/conf/distributions` (one-time setup: `docs/05-apt-repository.md`).

## CI

`.github/workflows/iso.yml` runs in a privileged `debian:trixie` container on push/PR: `tools/build-iso.sh --purge`, then `tools/boot-test.py`. On a `v*` tag it also uploads to SourceForge Files (`tools/upload-release.sh`, needs `SF_USER`/`SF_SSH_PRIVATE_KEY` secrets) and creates a GitHub release with only SHA256SUMS (the ISO is over 2 GB). `.github/workflows/community.yml` builds and checks community apps whose `repo/community/apps/` file a push or pull request changes (above). `.github/workflows/discord.yml` posts pushes to `main` (commit first lines) and `v*` tags to a Discord channel (secret `DISCORD_WEBHOOK`; nothing without it); `tools/discord-post-commits.py [--dry-run] GIT-LOG-ARGS` posts earlier commits the same way. Release checklist: `docs/06-ci-and-releases.md`.
